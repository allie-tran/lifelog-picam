# lifelog-picam

A lifelogging system that captures images and GPS from a Raspberry Pi camera,
uploads them to a server, and provides a web UI for browsing, searching, and
annotating the lifelog.

```
┌──────────────┐   encrypted     ┌─────────────────┐    REST/JSON   ┌──────────────┐
│  camera/     │   images + GPS  │   backend/      │ ◀────────────▶ │  frontend/   │
│  (Pi Zero 2W)│ ──────────────▶ │  FastAPI :8082  │                │  React :3000 │
│ capture +    │   HTTP upload   │  + Celery       │                │  (/selfhealth)│
│ watchdog     │                 │  PG / Mongo /   │                │              │
└──────────────┘                 │  Redis          │                └──────────────┘
                                  └─────────────────┘
```

The system has three components: a **camera client** (Pi), a **FastAPI backend**,
and a **React frontend**. Images are encrypted on the Pi with NaCl before upload
and decrypted server-side during ingest. After upload they flow through a
pipeline — segmentation (CLIP-embedding clustering), LLM activity annotation, and
day-summary generation.

---

## Components

### `camera/` — Raspberry Pi client
Two background processes, started from crontab via the shell wrappers:
- **`auto_capture.py`** (`auto_capture.sh`) — captures a still every 10 s with
  `picamzero`, reads GPS over serial NMEA, encrypts each image with PyNaCl, and
  writes it atomically to the `OUTPUT` dir.
- **`watchdog_monitor.py`** (`monitor.sh`) — watches `OUTPUT` for new files and
  uploads them (with their GPS sidecar) to the backend, retrying with backoff.

Device identity comes from a local `.env` (`DEVICE_ID`, `DEVICE_SECRET_KEY`,
`SERVER_PUBLIC_KEY`), generated by `setup.py`.

### `backend/` — FastAPI server (port 8082)
Single FastAPI app composed of `APIRouter` modules. Depends on PostgreSQL
(pgvector), MongoDB (user/auth + cached day summaries), and Redis (Celery broker
+ cache).

```
backend/
├── main.py            # app creation, router wiring, middleware, lifespan
├── core/              # config (env), dependencies, logging
├── routers/           # one APIRouter per area (auth, browse, retrieval, …)
├── schemas/           # Pydantic request/response models
├── services/          # business logic (segmentation, summary, embedding, …)
├── tasks/             # Celery app + tasks (segment/face/location/biometrics/…)
├── integrations/      # external clients: llm/ visual/ biometrics/ sessions/
├── database/          # SQLAlchemy models + the ImageRecord query helper
├── location/          # GPS pipeline + Foursquare enrichment
├── pipelines/         # post-upload orchestration
└── query_parse/       # free-text query parsing
```

Routers are mounted under their original prefixes (`/auth`, `/ingest`, `/browse`,
`/retrieval`, `/explore`, `/location`, `/images`, `/annotations`, `/face`,
`/delete`, `/notify`, `/status`) plus root-level day-summary endpoints. Interactive
API docs are served at `http://localhost:8082/docs`.

### `frontend/` — React/TypeScript SPA
`react-app-rewired` (CRA with overrides), Redux Toolkit, MUI. Hosted under
`/selfhealth/`. Components are grouped by feature under `src/components/`
(`search/`, `temporal/`, `spatial/`, `faces/`, `browse/`, `image/`, `meta/`, …).

## Running the services

### Backend
```bash
cd backend
# 1. API server
uvicorn main:app --host 0.0.0.0 --port 8082 --reload
# 2. Celery worker (separate terminal) — note the tasks.celery_app path
celery -A tasks.celery_app worker --loglevel=info
# 3. Celery beat for scheduled jobs (optional, separate terminal)
celery -A tasks.celery_app beat --loglevel=info
```
Requires a `.env` with at least: `PG_URI`, `JWT_SECRET`, `GEMINI_API`,
`GEMINI_MODEL_NAME`, `DIR`, `THUMBNAIL_DIR`.

### Frontend
```bash
cd frontend
yarn install      # use yarn — npm corrupts the lockfile here
yarn dev          # dev server (port 3000)
yarn build        # production build
```

### Camera (Pi only)
```bash
cd camera
python setup.py            # first-time: generate keys, enter server public key
python auto_capture.py     # capture loop
python watchdog_monitor.py # upload loop
# In production these run from crontab via auto_capture.sh / monitor.sh
```

### Database migrations
```bash
alembic upgrade head
alembic revision --autogenerate -m "description"
```

| Variable | Where | Purpose |
|---|---|---|
| `PG_URI` | backend, alembic | PostgreSQL (pgvector) connection |
| `JWT_SECRET` | backend | Auth token signing |
| `GEMINI_API` / `GEMINI_MODEL_NAME` | backend | LLM for segment annotation |
| `OPENAI_MODEL_NAME` | backend | Alternate LLM provider |
| `DIR` | backend | Root path for raw images |
| `THUMBNAIL_DIR` | backend | Root path for thumbnails |
| `LOCAL_PORT` | backend | API port (default 8082) |
| `DEVICE_ID` | camera | Camera device identity |
| `DEVICE_SECRET_KEY` | camera | Device NaCl secret key |
| `SERVER_PUBLIC_KEY` | camera | Server NaCl public key (image encryption) |

## Architecture notes
- Images are encrypted on the Pi with NaCl box encryption before upload and
  decrypted in the ingest pipeline.
- Segmentation groups consecutive images by CLIP cosine similarity
  (`SEGMENT_THRESHOLD`); a drop below threshold starts a new segment.
- `DaySummaryRecord` (MongoDB) caches computed day summaries; dirty flags trigger
  incremental or full regeneration.
- `database/types.py::ImageRecord` exposes a MongoDB-style API (`find`,
  `find_one`, `update_one`) over SQLAlchemy to ease the Mongo→Postgres migration.
- Auth uses JWT tokens plus per-endpoint access levels
  (`NONE`/`ANY`/`OWNER`/`ADMIN`) enforced via FastAPI `Depends`.

## Security notes (dev posture — review before any public deployment)
- **CORS** in `backend/main.py` includes a `*` wildcard with
  `allow_credentials=True`. Tighten to explicit origins for production.
- The camera **`BACKEND_URL`** is hardcoded in `camera/common.py` (no cert
  pinning).
- `setup.py` writes the device **secret key in plaintext** to `.env`; keep `.env`
  out of git (it is gitignored) and readable only by the owner.
